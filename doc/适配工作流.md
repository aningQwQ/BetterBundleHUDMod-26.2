# 版本适配工作流

面向下一次 Minecraft 版本适配的检查清单与经验记录。按顺序执行，避免重复踩坑。

## 一、先做决策

### 1. 问题归属

- 先判断问题是不是 `main` 核心代码的问题
- `main` 也有的问题，先在 `main` 修，再让兼容分支同步
- 兼容分支只做环境适配，不承载 `main` 缺失的功能修复

### 2. 分支形态

| 情况 | 做法 |
| --- | --- |
| 目标版本与现有兼容分支 API 同代 | 在现有分支用 Stonecutter 登记新版本 |
| 目标版本发生输入/渲染等 API 换代 | 从 `main` 新开兼容分支 |
| 目标版本与 `main` 差距较小 | 从 `main` 派生，直接回退差异 |
| 目标版本与 `main` 差距很大 | 从最近的兼容分支向上适配 |

判断“换代”的重点：输入事件（裸参数 vs `MouseButtonEvent` / `KeyEvent` / `CharacterEvent`）、渲染入口（`GuiGraphics` vs `GuiGraphicsExtractor`）、网络包签名。

### 3. 基线选择

- 从 `main` 派生时，`vcsVersion` 设为目标版本，能直接编译的代码不写条件分支
- 从旧兼容分支向上适配时，`vcsVersion` 保持旧基线，用 `//? if >=x.y.z` 隔离差异

## 二、确认环境

1. 本地是否已有纯净实例：`/mnt/ssd/MC/.minecraft/versions/<版本>-Fabric`
2. 查 Fabric Loader：实例 JSON 里的 `fabric-loader`
3. 查依赖版本，不要凭记忆：
   - Fabric API：`https://maven.fabricmc.net/net/fabricmc/fabric-api/fabric-api/maven-metadata.xml`
   - Cloth Config：`https://maven.shedaniel.me/me/shedaniel/cloth/cloth-config-fabric/maven-metadata.xml`
   - ModMenu：`https://maven.terraformersmc.com/releases/com/terraformersmc/modmenu/maven-metadata.xml`
4. 下载候选 jar，读 `fabric.mod.json` 的 `depends.minecraft` 确认范围，不要只看版本号
5. 依赖搭配参考：

| 1.21.4 | 0.119.4+1.21.4 | 17.0.144 | 13.0.4 |
| 1.21.5 | 0.128.2+1.21.5 | 18.0.145 | 14.0.2 |

## 三、构建配置

### 混淆版本（1.21.x 全系）

- Loom：`loom-back-compat` 0.4.3 + Loom 1.17.21，Gradle 9.5.1，JDK 21
- `loomx.obfuscated=true`
- mappings：`loomx.applyMojangMappings()`
- 模组依赖必须用 `modImplementation`，否则不会 remap
- Access Widener 头使用 `named`
- `fabric.mod.json` 的 `minecraft`、`cloth-config` 用属性展开，不要写死
- `accessWidenerPath`、`LICENSE` 在 Stonecutter 子项目里用 `rootProject.file(...)`
- 产物命名：`base.archivesName = "better-bundle-mc${minecraft_version}-v${mod_version}"`，并清空 `archiveVersion`

### 非混淆版本（26.x）

- 按 `main` 现有配置，Java 25，`implementation` 即可

## 四、常见 API 差异清单

从 26.x 向下适配到 1.21.x 时重点检查：

| 层 | 26.x | 1.21.x |
| --- | --- | --- |
| 渲染入口 | `GuiGraphicsExtractor` | `GuiGraphics` |
| 渲染方法 | `item/text/itemDecorations` | `renderItem/drawString/renderItemDecorations` |
| 注入入口 | `extractContents` | `renderContents` |
| 配置 | `AutoConfigClient` | `AutoConfig.getConfigScreen` |
| Bundle 重量 | `Fraction.result()` | `weight()` |
| 网络点击类型 | `ContainerInput` | `ClickType` |
| 屏幕访问 | `client.gui.screen()` | `client.screen` |
| 输入 | `MouseButtonEvent` / `KeyEvent` / `CharacterEvent` | 1.21.2–1.21.8 为裸参数；1.21.9 起为事件对象 |
| 窗口句柄 | `getWindow().handle()` | 1.21.2–1.21.8 为 `getWindow().getWindow()`；1.21.9 起为 `handle()` |
| 渲染矩阵 | `Matrix3x2fStack` | 1.21.2–1.21.5 为 `PoseStack`；1.21.6 起为 `Matrix3x2fStack` |

其他易错点：

- `ServerboundContainerClickPacket` 在 1.21.5 起：`slot` 为 `short`，`carriedItem` 为 `HashedStack`，第 6/7 参数顺序与旧版相反
- 1.21.6 起 `renderTooltip(Font, ItemStack, int, int)` 移除，改用 `setTooltipForNextFrame`
- 1.21.6 起 `InventoryScreen.render` 不再经过 `AbstractContainerScreen.render`，注入点要改用 `renderContents`
- 1.21.9 起 `Screen.hasShiftDown()` 移除，改用事件自带的 `modifiers()`
- 普通容器没有覆写 `charTyped`，字符事件走 `GuiEventListener` 默认实现；这是 `main` 的核心历史问题（issue #2），不要在兼容分支单独修

## 五、Stonecutter 注意事项

- `vcsVersion` 直接编译根 `src`，不经过生成；条件 `import` 会让基线版本编译失败，跨版本类型用全限定名
- 条件块内被注释的分支用 `/* ... *///?}` 形式
- `stonecutter.active '...'` 在 `stonecutter.gradle` 中配置
- 版本差异尽量只放依赖属性，代码差异用条件注释并保持最小
- 并行构建多个版本时，Loom 的 `remapJar` 偶发 `Failed to create service instance`；用 `./gradlew build --no-parallel` 或单版本构建

## 六、构建与部署

1. `./gradlew build --no-parallel`
2. 检查产物：`versions/<版本>/build/libs/better-bundle-mc<版本>-v<mod版本>.jar`
3. 解包确认：
   - `fabric.mod.json` 的 `minecraft` / `cloth-config` 范围正确
   - `better-bundle.accesswidener`、mixin 配置存在
   - class 数量与上一版本一致
4. 复制到实例 `mods/`，命名补发布序号：`better-bundle-mc<版本>-v<mod版本>-1.jar`
5. 同时安装匹配的 Cloth Config 和 ModMenu，校验 md5 或 `unzip -t`

## 七、测试清单

- 背包面板显示/展开/收起
- 箱子等普通容器面板显示
- 搜索框点击、聚焦、字符输入、中文拼音
- 空格批量塞入（含快速滑动）
- Shift 快速取出
- 一键整理（stateId 连续发包）
- Bundle 右键取出整叠
- 配方书界面
- 创造模式提示与禁用行为
- 面板布局、滚动、tooltip
- 鼠标残留幽灵物品

## 八、提交与发布

- 提交信息风格：`feat: 适配 Minecraft <版本>`、`feat: 支持 Minecraft <版本A> / <版本B>`
- 兼容分支不合并回 `main`
- 同一 Release 挂所有版本产物，补丁号统一 `-1`
- 产物命名：`better-bundle-mc<游戏版本>-v<mod版本>-<序号>.jar`
- 上传后更新 Release 说明：下载对应、环境、已知问题
- 已知问题要写清影响范围，不要把 `main` 核心问题写成兼容分支问题

## 九、收尾检查

- [ ] `main` 是否也需要同样的核心修复
- [ ] 兼容分支是否误带了 `main` 的功能修复
- [ ] 条件注释是否只在目标版本生效
- [ ] `settings.gradle` 是否残留本机绝对路径
- [ ] README / `doc/版本适配记录.md` 是否同步
- [ ] Release 附件是否齐全（jar + sources）
- [ ] 已知问题是否记录到 issue
