# 收纳袋整理策略实验结论（实验记录）

> 目的：量化「一键整理」的成本，以及写入策略（“塞法”）对**手动整理频率**的影响，
> 判断是否值得引入“三层预留”策略（给不可堆叠物品常驻空袋）。
>
> 方式：纯 Python 复刻 `BundlePacker`（三层装箱 + `realize` 腾挪/缓冲），无 Minecraft 依赖。
> 脚本：`tools/sort_move_sim.py`（可复现）。
> 结论：**发行版（同种优先 → 最空袋 worst-fit）在手动整理频率上最优，维持现状；
> 三层预留仅作实验特性，不默认启用。** Java 代码已回退，仅保留本目录。

---

## 1. 背景

- 原版重量规则：不可堆叠物品（maxStack=1）单件即占满整袋（64/64），**必须有一个空袋才能放入**。
- 发行版写入/整理规则：`同种优先 → 否则最空袋（worst-fit）`。
- 实验方案“三层预留”：`L1 同种 → L2 非预留 worst-fit → L3 预留 best-fit`，
  按比例（`RESERVE_RATIO=0.25`）保留“当前最空”的若干袋，平时不写入，留给不可堆叠物品。

---

## 2. 整理步数随占用率 p 的近似函数

对分桶均值（每桶约 400~600 样本）拟合：

```
f(p) ≈ A/(1−p) + B·p + C·p²        （p = 已用重量 / (K×64)）
```

| 策略（K=8） | f(p) ≈ | R² |
|---|---|---|
| 旧·最空法 worst-fit（发行版） | `0.22/(1−p) − 11.4·p + 19.8·p²` | 0.83 |
| 当前·留空法 reserve（三层预留） | `0.11/(1−p) − 17.3·p + 39.6·p²` | 0.94 |
| 最紧法 best-fit | `0.08/(1−p) + 11.1·p + 23.1·p²` | 0.95 |

- `A/(1−p)`：接近装满时的“先挪开挡路”腾挪开销（三者接近，p→1 发散）。
- `B·p + C·p²`：写入态偏离整理目标的“重排”开销——**策略差异几乎全在这里**。
  发行版 ≈0（天生对齐），三层预留中等，最紧法最大。

p=0.9 首次整理步数：worst ≈ 7，reserve ≈ 13，best ≈ 26。

---

## 3. 手动整理频率（关键结论）

测法：从空袋开始逐次塞入，每塞一次就算一次“现在整理要几步”；
`≥2 步`即视为乱到需要手动整理一次，整理后继续。各 100 seeds 平均，满仓约 16 次塞入。

| 塞法 | 手动整理次数 | 大约每 N 次塞入整理一次 | 最长一次不整理 |
|---|---|---|---|
| 旧·最空法 worst-fit（发行版） | **~2.3 次** | **~7 次塞入** | 19 次 |
| 当前·留空法 reserve | ~4.3 次 | ~3.6 次塞入 | 14 次 |
| 最紧法 best-fit | **~8.2 次** | **~2 次塞入** | 8 次 |

（阈值放宽到 3 步时：发行版 ~1.9 次 / 每 8.5 次；reserve ~3.7 次 / 每 4.3 次；best ~7 次 / 每 2.2 次。）

**读法**：
- 发行版塞满一整轮只需手动整理约 2 次，且多数档几乎全程不用整理。
- 最紧法几乎每塞 2 次就要整理一次（最费手）。
- 三层预留居中，但相对发行版**手动整理频率约翻倍**。

---

## 4. 扰动（整理后又用了/塞了东西）再整理

“整理一次 → 随机搬动 20% → 再整理”，统计再整理步数（K=8，400 seeds）：

| 扰动粒度 | p=0.1 | p=0.9 | 三策略差异 |
|---|---|---|---|
| 整叠搬 | ~0 | ~1 | 有（worst 最省） |
| 每种 5 个一捆 | ~1.6 | ~14 | 很小 |
| 单个打散 | ~4.7 | ~40 | 几乎没有 |

**结论**：一旦被打散，成本主要来自“重新聚堆”，三种塞法差别很小；
“塞法”的差别只体现在**从乱到整齐的第一次整理**上。

---

## 5. 最终结论

1. **决定“是否需要频繁手动整理”的是写入策略（塞法），不是整理算法本身。**
2. **发行版（worst-fit）最优**：手动整理最少、最简单；唯一短板是**不留空袋 → 不可堆叠塞不进**。
3. **最紧法（best-fit）应避免**：手动整理频率约为发行版 4 倍，且整理搬动大。
4. **三层预留**：用“常驻空袋”换不可堆叠可放，代价是手动整理频率约翻倍（~2→~4 次/满仓）；
   对**不常带工具**的玩家是净退步，只有**经常带不可堆叠**时才划算。
5. 纯客户端无法突破“不可堆叠占整袋”，因此“软预留”是客户端内相对合理的落点；
   若要彻底不费手，只能走自研容器 / 服务端方案。

**决定**：发行版保持现状（同种优先 → 最空袋），三层预留作为**实验特性**保留在本目录，
不默认改变游戏手感。Java 侧改动已回退。
